# Focus 01 — Architecture and Data Flow (binlog_server @ 99de682)

## Findings

### F1. One binary, six short-lived/long-lived modes; no daemon RPC surface
- `src/app.cpp:25-48` -> `operation_factory::create` (`src/operations/operation_factory.cpp:43-82`) dispatches `argv[1]` to a `generic_operation<mode>`. Exit code = `execute()` bool.
- `fetch` / `pull` are the only writers (storage built in `streaming` mode, `fetch_operation.cpp:80-81`, `pull_operation.cpp:109-110`). `list`, `search_by_timestamp`, `search_by_gtid_set` build `querying_only` storage (`list_operation.cpp:51`, `search_by_*_operation.cpp:57/60`); `purge_binlogs` builds `purging` storage (`purge_binlogs_operation.cpp:57`). Query/purge print a JSON response on stdout (`purge_binlogs_operation.cpp:66-86`).
- So the "cluster" is: MySQL source <-(libmysqlclient)- PBS writer process -> storage (dir or S3 bucket) <- other PBS processes (query/purge) ; and in `pull`, PBS -> downstream clients over a home-grown MySQL server protocol.

### F2. Ingress path (source -> storage), shared by fetch and pull
1. `collector_context::receive_binlog_events` (`collector_context.cpp:125-205`) opens a libmysqlclient connection, then `open_connection_and_switch_to_replication` (`:207-272`) picks COM_BINLOG_DUMP_GTID (storage GTID set; empty storage first reads `SELECT @@GLOBAL.gtid_purged`, `:229-240`) or position dump (current binlog name + `get_current_position()`, `:253-261`).
2. Each packet: strip 0x00 prefix (`:154-158`), parse into `event_view` against `reader_context` (FSM ROTATE(art) -> FDE -> PREVIOUS_GTIDS? -> (GTID <any>*)* -> ROTATE|STOP?, `reader_context.hpp:~88-104`; 32 `logic_error` raise sites in `reader_context.cpp`).
3. Optional rewrite path synthesises ROTATE/FDE/PREVIOUS_GTIDS and rewrites positions/checksums (`collector_context.cpp:274-429`).
4. `process_binlog_event` (`:431-491`): artificial ROTATE -> `open_binlog` / reuse open file (`:493-572`, position check raises `logic_error` at `:528-532`); `storage::write_event` buffers; non-artificial ROTATE/STOP -> `close_binlog` (flush).
5. `storage` facade (`storage.cpp:143-202`) keeps an in-memory event buffer, and flushes only up to the last transaction boundary on size/interval checkpoint, on close, on timeout-disconnect (`collector_context.cpp:195-200`) and in the destructor (`storage.cpp:68-77`).
6. `storage_core::write_event_block` (`storage_core.cpp:299-322`) under unique lock: (a) encrypt (AES-CTR from offset) + append data to backend stream, (b) bump in-memory `size`/GTIDs/timestamps/seq_no, (c) `put_object(<binlog>.json)`. **Data is persisted before metadata**; restart recovery truncates the tail file to metadata size (`storage_core.cpp:956-984`) and refuses if metadata > actual size (`:974-977`) or any non-tail mismatch (`:968-972`).
7. New binlog creation order (`storage_core.cpp:680-703`): open_stream(create, truncating) -> write magic -> push record -> `put_object(<binlog>.json)` -> `put_object(binlog.index)`. Restart validator rejects any object not in the index (`:779-782`). Confirms the mechanism of the open ticket "A crash while a new binlog is being created leaves a storage that cannot be opened": a kill between `:686` and `:701` leaves an unindexed data (and maybe .json) object -> `fetch`/`pull` cannot start. Prime Antithesis target (process kill during rotation).

### F3. Persistence formats / serialization boundaries
- Storage root contents: `metadata.json` (mode + encryption format, `storage_core.cpp:828-834`), `binlog.index` (text, `./<name>\n`, `:789-799`), per-binlog `<name>` (raw/encrypted binlog bytes) + `<name>.json` (size, previous/added GTIDs, min/max ts, last_sequence_number, encryption envelope, `:907-925`).
- Filesystem `put_object` = write `<name>.tmp` + fsync + rename + dir fsync (`filesystem_storage_backend.cpp:128-158`). Stream data: `ofstream` write+flush, **no fsync** (`:229` TODO) — confirms the mechanism of the open "never synced" ticket; only matters for power loss/OS crash, not process kill.
- S3: stream data is a local temp file; **every** `write_data_to_stream` re-uploads the whole file via PutObject (`s3_storage_backend.cpp:850-863, 931-936`); append mode re-downloads the object first (`:828-832`). `do_fsync` is a no-op (`:815-819`). Confirms the "full re-upload per checkpoint" ticket mechanism. Recovery `resize_object` on S3 = download, truncate, re-upload (`:765-808`).
- Wire: MySQL frames in `minimysql/network_io_operations.cpp` (payload size checks at `:97`, `:144`); GTID set binary encoding for COM_BINLOG_DUMP_GTID (`collector_context.cpp:242-251`); JSON config via nv_tuple (`replication_source_config.hpp:32-35` etc.).

### F4. Egress path in `pull` (storage -> downstream clients) and its threading
- `pull_operation.cpp:113-161`: main thread runs `io_ctx.run()` which hosts the `network_service` listener and **all** client sessions as coroutines on a single thread (`network_service.cpp:633-690`, `co_spawn(... detached)` at `:662`). A separate `std::jthread` runs the collector loop with reconnect/idle (`:125-158`).
- The only shared object across the two threads is `binsrv::storage` (same `storage_ptr`). Writer touches facade fields (event buffer, checkpoint state) only from the collector thread; sessions only call `storage::fetch_event_block` (`sender_context.cpp:226, 484`) -> `storage_core::fetch_event_block` under `shared_lock` (`storage_core.cpp:461`). In-process safety rests on that `std::shared_mutex` (`storage_core.hpp:275`).
- Readers only see **flushed** bytes: `fetch_event_block` clamps to `record_it->size` (`storage_core.cpp:513-538`), and size is bumped only after the backend write. At EOF of a file it moves to the next record, else returns length-0 EOF (`:523-532`); empty storage returns EOF (`:474-478`, PBS-91).
- `handle_binlog_dump_command` (`network_service.cpp:279-334`): 1 MiB blocks, blocking dumps poll storage every 500 ms on EOF; non-blocking send EOF packet. `sender_context` FSM synthesises artificial ROTATE+FDE and errors on a partial event at a file switch (`sender_context.cpp:403-436`).
- **Architectural hazard (not ticketed as such):** storage I/O is synchronous on the io thread. `fetch_event_block` performs `backend_->get_object` (S3 GET or file read) plus decryption while holding the shared lock, on the single io thread; meanwhile the collector's `write_event_block` holds the unique lock across an S3 PutObject of the whole file. A slow S3/disk therefore stalls every session, the acceptor and the SIGTERM handler at once. This is a liveness/latency property (e.g. "a blocking dump client receives a newly flushed transaction within N s"), not a safety bug.

### F5. Reconnect and failure classification (pull/fetch)
- Connect / switch-to-replication failures are caught and return false (`collector_context.cpp:212-216, 263-267`) -> pull sleeps `idle_time` and retries (`pull_operation.cpp:137-153`).
- During streaming only `CR_SERVER_LOST` is treated as "disconnect"; any other client error raises `core_error` (`easymysql/connection.cpp:537-554`), which is **not** caught in `receive_binlog_events`, propagates to the pull thread's catch (`pull_operation.cpp:154-157`), stops io_ctx and the process exits non-zero. Same for any `reader_context` `logic_error`, the rotate-position mismatch, or a storage write error (ENOSPC/S3 failure). So `pull` is a "crash-on-anything-but-2013" supervisor-dependent service. Antithesis should run it under a restart loop and assert restart-recoverability rather than in-process survival.
- On timeout-disconnect the buffer is truncated to the last boundary and flushed (`collector_context.cpp:195-200`); on exception it is not discarded, but the destructor flush only writes through `last_transaction_boundary` (`storage.cpp:276-302`), so no partial transaction should land.
- Shutdown latency: SIGTERM stops io_ctx, but the collector only checks `io_ctx.stopped()` between events (`collector_context.cpp:151`); a blocked `mysql_binlog_fetch` holds shutdown for up to `read_timeout`.

### F6. Cross-process concurrency on one storage (the real distributed boundary)
- No cross-process lock exists: only the in-process `shared_mutex`; `.tmp` names are deterministic (`filesystem_storage_backend.cpp:140-142`). Confirms mechanism of the open "two fetch instances corrupt" ticket.
- A streaming storage loads `binlog.index` once in the constructor (`storage_core.cpp:214`) and never re-reads it; a concurrent `purge_binlogs` therefore diverges from the writer's in-memory list (mechanism of the purge-vs-fetch ticket confirmed). README.md:473 explicitly says this combination "should be avoided", so it is documented misuse — model it as an operator error, not a safety property.
- Querying modes are designed to coexist with a writer: the constructor tolerates a missing index (`storage_core.cpp:189-195`), skips index/object reconciliation (`:766-770`) and drops records with bad metadata (`:942-950`). **New lead (not in the ticket snapshot):** filesystem `do_list_objects` calls `dir_entry.file_size()` per entry (`filesystem_storage_backend.cpp:114`), which stats the path after readdir. The writer creates and renames `<binlog>.json.tmp` on every flush (`:141-153`), so a `list`/`search_*` that runs during a flush can throw "No such file or directory" before `remove_temporary_objects` filters `.tmp` names (`storage_core.cpp:597-614`). It also throws on any non-regular entry (`:108-111`). I checked the code only; this needs a reproduction. Candidate property: "query modes run concurrently with fetch/pull never fail spuriously".

## Assumptions
- libstdc++/libc++ `directory_entry::file_size()` re-stats (only the file type is cached from readdir). This is standard behaviour, but I did not test it on the build toolchain.
- Antithesis faults are process kill/pause and network faults, not power loss, so the "no fsync on data" gap is low-yield there.
- A network partition or source kill shows up in libmysqlclient as `CR_SERVER_LOST` (2013). If it shows up as another code, pull exits instead of reconnecting (see Open questions).
