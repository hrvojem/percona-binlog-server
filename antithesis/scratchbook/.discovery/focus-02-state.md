# Focus 2 — State management and persistence

## Findings

**Persistent state map (verified in code).** One storage = flat namespace of objects: `metadata.json` (only `mode` + `encryption` format, `storage_core.cpp:828-834`), `binlog.index` (newline list `./<name>`, `:789-799`), per binlog `<name>` (raw, optionally AES-CTR ciphertext) + `<name>.json` (size, previous/added GTIDs, min/max ts, last_sequence_number, encryption envelope, `:907-925`). Resume position is derived entirely from the **last record's metadata**: position = `size`, GTIDs = `previous_gtids ∪ added_gtids` (`storage_core.hpp:313-337`; used at `collector_context.cpp:242-260`). Data bytes are never parsed on open (TODO `storage_core.cpp:785`), so metadata is the single source of truth for both resume and what `pull` readers may see (`fetch_event_block` bounds reads by in-memory `record.size`, `:513-538`).

**Persistence primitives.** Filesystem `put_object` = write tmp, fsync, rename, fsync dir (`filesystem_storage_backend.cpp:127-160`). The binlog data stream is appended with `ofstream` unbuffered + `flush()` but **no fsync** (TODO `:229-230`). S3 `put_object` = single PutObject (atomic); the data "stream" is a local temp file re-uploaded whole on every block (`s3_storage_backend.cpp:850-862, 933-938`); `do_fsync` is a no-op (`:815-819`). No explicit multipart code; S3-CRT may split large PUTs internally, but an aborted PUT leaves the previous object version intact, so crash mid-upload is recoverable (object ≥ metadata size → truncate). S3 `resize_object` = download, truncate locally, re-upload (`:765-808`) — idempotent on retry.

**F1. Write ordering is data → in-memory size → metadata; failure leaves buffer un-erased → duplicate write (ticket 18, CONFIRMED).** `write_event_block` (`storage_core.cpp:299-322`) writes stream, does `size +=` (310) and `added_gtids +=` (314) *before* `save_binlog_metadata` (321). `flush_event_buffer_internal` erases the buffer only after `write_event_block` returns (`storage.cpp:286-296`). After an exception, `~storage` flushes again (`storage.cpp:68-77`), and so does `collector_context.cpp:200` on disconnect. Metadata-save failure → data written twice and metadata size matches the doubled file → passes startup validation forever. On S3, a failed data upload also re-appends to the local tmp file (stream state not rolled back). On filesystem, a failed data write puts `ofs_` into fail state so the repeat fails (consistent with ticket's "data write handled"). Also: the in-memory GTID set is advanced even when metadata is not saved — the `pull` replication source can serve bytes that are not durable. Antithesis angle: S3/disk faults at the exact metadata PUT; property "stored binlog is byte-prefix of source binlog".

**F2. New-binlog creation is a 3-step non-atomic sequence that is fail-stop on crash (ticket 15, CONFIRMED).** `open_new_binlog_file_internal` (`storage_core.cpp:680-703`): write magic (file created by `open_stream` w/ `trunc`; on S3 the object is uploaded on that first write), then `<name>.json`, then `binlog.index`. Startup in streaming/purging mode rejects any object not in the index (`:779-783`), metadata without index entry (`:993-996`), or a non-empty storage without index (`:187-198`). A kill between any step → `fetch`/`pull`/`purge_binlogs` all refuse to start until manual repair. Only `.tmp` objects are auto-cleaned (`:597-630`). Rotation happens every binlog, so this window is hit routinely under kill faults. An MTR test exists (`storage_interrupted_binlog_creation.test`).

**F3. purge_binlogs commits index first, deletes after; partial delete = permanently unopenable (CONFIRMED, partly documented).** `purge_binlogs` (`storage_core.cpp:369-433`): rewrite index, then best-effort `remove_objects` (metadata then payload per victim). The code comment says leftovers "will trip the constructor's validators on next startup"; README:443 only says "partial success / warning". Since `purge_binlogs` itself constructs storage with the same validators (`purge_binlogs_operation.cpp:56`, validation is skipped only for `querying_only`), the operator cannot even re-run purge. Crash or S3 DELETE failure mid-batch reaches it. Property candidate: after any purge outcome, the storage still opens (currently expected to fail → bug-finding property).

**F4. No cross-process lock; in-memory record list overwrites the index (tickets 9 & 24, CONFIRMED).** No `flock`/lockfile/O_EXCL anywhere in `src`. A running `pull`/`fetch` keeps `binlog_records_` in memory and rewrites the whole index from it at every rotation (`save_binlog_index`, `:789-799`), resurrecting entries a concurrent `purge_binlogs` removed → next start fails "binlog index contains a reference to a non-existing object". README:473 explicitly says concurrent purge+fetch "may cause data corruption and should be avoided" — documented limitation, so a property should treat it as out-of-contract (or test that the *workload* respects it).

**F5. Filesystem binlog data not fsynced while metadata is (ticket 19, CONFIRMED in code).** After power loss metadata `size` can exceed file size → recovery refuses (`storage_core.cpp:974-978`). Reachability in Antithesis is doubtful: process/container kills do not drop the page cache (see Open questions).

**F6. Startup auto-recovery is tail-only, truncate-only.** Size mismatch on any non-last binlog = fatal (`:968-972`); last binlog larger than metadata → truncate (`resize_object`, `:979`); smaller → fatal. Combined with F1 this means recovery can "succeed" on corrupted data. Claimed guarantee worth testing: "after improper shutdown the tail binlog is truncated to the last checkpoint and streaming resumes".

**F7. New lead: querying modes racing a writer on filesystem.** The constructor explicitly tolerates concurrent query-only operations (`storage_core.cpp:189-194`, `:766-770`, `:942-950`), so concurrent `list`/`search_*` during `fetch`/`pull` is an intended use. But `do_list_objects` calls `dir_entry.file_size()` (`filesystem_storage_backend.cpp:114`) — a fresh `stat` — on entries like `binlog.000003.json.tmp` that every checkpoint creates and immediately renames away (`:144-154`). A rename between `readdir` and `stat` would throw `filesystem_error` and fail the query. Not reproduced; pure timing bug, ideal for Antithesis. Second variant: a query that loads an old index while every listed metadata disappears (only possible with concurrent purge, out-of-contract) reaches `binlog_records_.front()` on an empty vector (`:1001`, ticket 13 mechanism).

**F8. GTID-mode resume across source rotation (ticket 14, mechanism CONFIRMED).** On reconnect, an artificial ROTATE naming a different file makes the collector `close_binlog()` the old one without writing a ROTATE event (`collector_context.cpp:541-553`), and intermediate empty source binlogs are never created. The stored state then diverges from the source byte-for-byte. Position mode resumes via name+offset and is checked (`:522-532`).

**F9. Checkpointing defines the loss window, and the readers only see flushed data.** Without `checkpoint_size`/`interval`, data is persisted only at rotation, disconnect, or graceful shutdown (`storage.cpp:179-215`, `collector_context.cpp:195-200`, destructor). A kill loses the whole unflushed tail; resume re-requests it from the source, which is safe only while the source retains it. The `pull` source cannot serve those events until they are flushed. Graceful SIGTERM: `receive_binlog_events` returns without discarding (`:178-183`) and the destructor flushes complete transactions only. Property: "after any kill and restart, storage = prefix of source ending at a transaction boundary; after catch-up = exact copy".

**F10. Storage identity is not persisted (ticket 25, CONFIRMED).** `metadata.json` holds only mode and encryption format; nothing ties a storage to a source server UUID. A source failover or `RESET BINARY LOGS` is a state-consistency hazard (position resume past EOF, or silent append of another server's history).

**F11. Minor/latent.** After load, `purged_gtids_ = front().added_gtids` (`:1001-1004`, asserted at `:219-220`). Semantically this should be `previous_gtids`. It is harmless today because `purged_gtids_` is read only when the storage is empty (`storage_core.hpp:318-319`). Encryption: appends reuse the file's own envelope (`:715`, `:308`), so the old KEK must stay in the keyring; turning encryption on for an existing storage rewrites `metadata.json` (`:175-178`), which gives a mixed storage by design. When `fs_buffer_directory` is configured, S3 temp files left by a crash are never cleaned, because the names are new UUIDs every run (`s3_storage_backend.cpp:929-931`, `:646-648`).

**Concurrency in-process.** The collector and the `pull` sender share `storage_core` through a `shared_mutex`. `fetch_event_block` holds the shared lock across backend I/O, including S3 GET and decryption (`:461-563`), while writers need the exclusive lock. So many or slow readers can stall the collector, and it is not known whether the rwlock prefers readers. Readers never see an intermediate state of a single `write_event_block` (exclusive lock across data + metadata). After an exception, though, they can see the in-memory size that F1 left incremented.

## Assumptions
- S3 PutObject is atomic, and an aborted CRT multipart upload never replaces the object. This is S3 semantics and was not verified against the MinIO/Versity used in testing.
- libstdc++ `directory_entry::file_size()` re-stats on POSIX (F7). This was not checked against the libstdc++ source.
- A failed `ofstream` write leaves the stream in the fail state, so the destructor re-flush fails on the filesystem backend. Ticket 18's disk sweep agrees.
