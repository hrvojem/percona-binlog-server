# Focus 05: Liveness guarantees

Commit 99de682. "Claims" are what the README or code comments promise. Each is something to test, not something already shown to hold.

## Findings

**L1. Pull reconnects after network errors (claim, README:3, 377-378).** The loop is in `pull_operation.cpp:118-148`: `receive_binlog_events`, then `wait_for_interruptable(idle_time)`, then reconnect. In `collector_context.cpp:207-272`, a failed connect or a failed switch to replication is caught (`easymysql::core_error`) and returns false, so pull retries. Inside the event loop, though, `connection::fetch_binlog_event` (`connection.cpp:537-555`) throws `core_error` for every errno except `CR_SERVER_LOST`. Nothing in `receive_binlog_events` catches it. It reaches the operation thread's `catch(...)` (`pull_operation.cpp:142`), the whole process exits, and pull never reconnects. So the claim holds only if every network fault shows up as 2013. A server error packet mid-stream (1236 for a purged or missing binlog, a shutdown or kill message) ends pull for good. Reset-source and purged-GTID scenarios are terminal by design, which matches ticket 25 ("exits 1 at every run").
- MTR `pull_mode.test` survives a graceful shutdown and a kill -9 of the source, so the common paths do arrive as 2013. Antithesis-style faults (RST in the middle of a packet, partition during the handshake, pause of the source) have not been tried.
- Property: **"pull process stays alive across source and network faults that the source recovers from"** (sometimes/always-style: no unexpected exit while the source is reachable again), plus **"after the source has been reachable for idle_time + connect_timeout + ε, a new event committed on the source appears in storage"**.

**L2. Capture latency is bounded by idle_time and read_timeout.** The connection is opened in blocking mode (`pull_operation.cpp:112`). Heartbeats are disabled: `MYSQL_RPL_SKIP_HEARTBEAT` (`connection.cpp:202`), and no `@master_heartbeat_period` is ever set. On an idle source the client therefore disconnects after every `connection.read_timeout`, sleeps `replication.idle_time` in 1 s steps (`pull_operation.cpp:57-78`), and reconnects. Worst-case delay before a new source event reaches pull's memory is about idle_time + connect time. A silent partition (half-open TCP) is noticed only through read_timeout.
- `connection.read_timeout`, `connect_timeout` and `idle_time` are not validated (`replication_config.cpp:26-37`; the easymysql config has no timeout checks). With read_timeout = 0, libmysql has no read timeout, so a half-open connection may hang pull forever, and SIGTERM with it. I have not confirmed the libmysql semantics of 0 (see open questions). `idle_time = 0` gives a tight reconnect loop against a down source; connect_timeout bounds each iteration.

**L3. Checkpoint flushing is driven by incoming events, not by a timer (code comment `storage.cpp:173-201`; README:626 implies "after the interval").** The interval check runs only inside `storage::write_event`. If a complete transaction is buffered and no further event arrives, nothing is flushed until (a) a ROTATE/STOP closes the file (`close_binlog`, `storage.cpp:204-215`), (b) read_timeout expires and the connection drops (`collector_context.cpp:195-200`), or (c) shutdown runs the destructor (`storage.cpp:68-77`). Ticket 2's own wording agrees ("flushed on the first event after T has passed"). Ticket 2 is fixed: the config read is back at `storage.cpp:55-65`.
- Without checkpoint settings, data from the current binlog reaches the backend only at rotation (up to max_binlog_size), on disconnect, or on shutdown. The in-memory `event_buffer_` grows to match, which also bounds RAM.
- Property: **"with checkpoint_interval = T and read_timeout = R, a transaction that is complete in the source's binlog is on the backend within roughly min(T + next-event gap, R) + flush time"**, and with size checkpointing, unflushed committed bytes stay at or below checkpoint_size plus one transaction (that half is the safety side, ticket 2's property).

**L4. The replication source sees only flushed data, so replica freshness inherits L3.** `storage_core::fetch_event_block` (`storage_core.cpp:436-564`) reads up to `record.size`, and only `write_event_block` advances that (`storage_core.cpp:310`). End-to-end liveness, "an event committed on the source is eventually served to a blocking dump client", therefore depends on checkpointing, idle cycles and rotation. Without checkpointing, a replica may see nothing of the active binlog for a long time while the source writes continuously.

**L5. A blocking dump polls empty storage until data arrives (PBS-91, claim in `storage_core.hpp:216-224` and `storage_core.cpp:463-478`).** Empty storage returns EOF with `binlog_name` left unchanged, and `handle_binlog_dump_command` polls every 500 ms (`network_service.cpp:293-320`). Covered by MTR `rs_blocking_dump_empty_storage.test`. Some liveness gaps remain:
- A named binlog that is not in storage yet (client ahead of pull), or an offset past `record.size` (client ahead of the flushed position, for example after pull lost unflushed data in a crash), returns `false`. The session then `co_return`s without sending an error packet (`network_service.cpp:308-313`). The client sees the connection drop, so it makes progress only if it reconnects by itself. Unlike the empty-storage case, there is no "wait until it appears".
- While polling, the session sends nothing: no heartbeats, and the client's socket is never read. A dead or partitioned replica is detected only when the next write times out (`write_timeout`), so idle sessions on a quiet storage stay alive indefinitely. The EOF path does no backend I/O, so each poll is cheap.
- Property: **"a blocking dump client connected before any data, or caught up at EOF, eventually receives every event later flushed to storage, in order"**.

**L6. The io_ctx thread does blocking storage I/O, so one slow or stuck read or write stalls signals and every session.** Signals (`pull_operation.cpp:100-104`), the listener and all sessions run on the single `io_ctx.run()` thread. `sender_context::get_event` calls storage synchronously, and `fetch_event_block` holds a `shared_lock` across `backend_->get_object` (an S3 GET), decryption included (`storage_core.cpp:461,539-558`). The collector holds a `unique_lock` across `write_data_to_stream` plus the metadata save (`storage_core.cpp:305-321`). On S3, that is a whole-object re-upload (ticket 17: O(S²/C) bytes). Consequences:
  - Every replica session and SIGTERM handling wait for the collector's S3 PUT, and the PUT time grows with the size of the binlog.
  - **Ticket 7 escalates (validated).** `indexed_event_block.cpp:31-50` only `assert`s `event_size >= 19`. With NDEBUG, `event_size == 0` never advances `offset` and keeps calling `push_back`. `compute_fetch_size_requirements` (`sender_context.cpp:358-370`) returns `ready` for a first event of size 0, so this path is reachable. The loop runs on the io_ctx thread, so it hangs **all** sessions and the SIGTERM handler, not one replica. Pull can then only be stopped with SIGKILL, and memory grows without limit. The collector thread checks `io_ctx.stopped()` and keeps running.
- Property: **"SIGTERM to pull completes within a bound"** (README:719 claims read_timeout + 1 s), and **"a stalled or corrupt replica session does not delay others"**.

**L7. Graceful termination: the claimed bound is incomplete.** The README:719 bound (read_timeout + 1) leaves out several waits. During them the `jthread` destructor joins after `io_ctx.run()` returns (`pull_operation.cpp:121,145-147`):
  - `mysql_real_connect` (connect_timeout);
  - the `SET @source_binlog_checksum` and `SELECT @@GLOBAL.gtid_purged` queries (read_timeout);
  - a checkpoint or close flush in progress (unbounded S3 PUT under SDK default timeouts and retries: `s3_storage_backend.cpp:189`, no app-level timeout);
  - the destructor's final flush (`storage.cpp:68-77`);
  - creating the S3 client (ticket 16: about 6 s IMDS wait outside EC2).
  A signal during the event loop returns via case (1) (`collector_context.cpp:178-183`) without `flush_event_buffer`. The destructor flushes instead, and **swallows every exception**, yet pull still logs "successfully shut down" and returns success (`pull_operation.cpp:155-160`). A failed final flush therefore exits 0. That is a safety lead for the durability focus.
- Fetch mode has the same signal structure (`fetch_operation.cpp:69-105`) and must terminate when it reaches EOF (non-blocking dump, case 3).

**L8. Permanent stop at a ≥16 MB event (ticket 10, validated in the ticket end to end; mechanism: `network_io_operations.cpp:~146` rejects frames ≥ 0xFFFFFF).** A replica reconnects to the same position and fails again, so replication stops for good. Property: **"replica progress eventually passes every stored event"**.

**L9. Liveness lead for the safety focus (code reading only, not run): an artificial ROTATE can be skipped at the file switch while the next file is still empty.** `open_new_binlog_file_internal` publishes the new record at size 4 (`storage_core.cpp:686-698`). A sender at EOF of binlog N calls `fetch_event_block`, which moves on to N+1 at offset 4 with read_length 0 (`storage_core.cpp:524-541`) and returns true with an empty buffer and `binlog_name = N+1`. `populate_event_block` then takes the EOF path (`sender_context.cpp:484-490`) before `handle_binlog_file_switch` runs. On the next call `saved_binlog_name == N+1`, so `fsm_state_` never becomes `start_from_beginning`, and the artificial ROTATE plus the FDE checksum refresh for N+1 are skipped. The window lasts from the rotation until the first flush of N+1, which is long without checkpointing. MTR `rs_blocking_dump`/`rs_tail_reuse` may or may not cover this timing.

**L10. Wedge states that prevent progress after a restart** (tickets 9, 13, 15, 18, 19, 25). Each leaves a storage that `binlog_server` refuses to open or resume, so every later pull or fetch exits. I did not re-validate these; they belong to other focuses. Liveness view: **"after any crash or fault, a restarted pull eventually resumes without manual intervention"**.

## Assumptions
- libmysql reports read timeouts and peer resets as `CR_SERVER_LOST`. `pull_mode.test` supports this for shutdown and kill; I did not check it against libmysql source.
- Release builds use NDEBUG (ticket 7's infinite loop depends on it).
- Filesystem `read_file_content` with a zero-length range returns empty, as S3 does explicitly at `s3_storage_backend.cpp:277`.

## Open questions
- [needs-check] What does libmysql do with `MYSQL_OPT_READ_TIMEOUT = 0`: no timeout, or the default? Should the config reject 0 the way `replication_source` does?
- [needs-check] Which error codes reach `fetch_binlog_event` when the source shuts down gracefully, is KILLed, or partitions in the middle of a packet? Any code other than 2013 terminates pull (L1).
- [needs-repro] L9 artificial-ROTATE skip at the switch to an empty next binlog: confirm with mysqlbinlog against pull during a source rotation.
- [design] Is "interval checkpoint fires only on the next event" (L3) intended, or should a timer flush? This decides how tight the freshness property can be.
- [design] Should the dump session send heartbeats or an error packet (1236) instead of closing silently (L5)?
