# Focus 9 — External dependencies and integration points

Commit 99de682. Pinned deps (CMakeLists.txt:80-85): Boost 1.90.0 EXACT (url/json/asio), AWS SDK C++ 1.11.774 EXACT (s3-crt only), libmysqlclient (any; README says 8.0.x), OpenSSL::Crypto, ZLIB.

## Findings

### A. MySQL source via libmysqlclient (src/easymysql)

1. **Only CR_SERVER_LOST is a "soft" failure; every other fetch error kills `pull`.** `connection::fetch_binlog_event` returns `false` silently only when `mysql_errno == CR_SERVER_LOST`, otherwise raises `core_error` (connection.cpp:546-551). In `collector_context::receive_binlog_events` a `false` is treated as "timed out" (collector_context.cpp:172-204) and pull goes idle/reconnects (pull_operation.cpp:137-153); a thrown error escapes the jthread, `io_ctx.stop()` and the process exits (pull_operation.cpp:154-166). So a server-side error packet during the dump (e.g. ER 1236 "position > file size" / purged binlog — the ticket 18/25 states) is terminal, while TCP reset, read timeout and half-open sockets all collapse into the same CR_SERVER_LOST "idle and retry" path. Connect/handshake/`SET @source_binlog_checksum`/`SELECT @@GLOBAL.gtid_purged`/`mysql_binlog_open` failures are caught as `core_error` and retried (collector_context.cpp:209-267). Non-`core_error` exceptions there (e.g. a gtid_purged string that fails `gtid_set` parsing, line 232) are fatal.
2. **Read timeout is the idle detector; no heartbeats.** Dump flags always include `MYSQL_RPL_SKIP_HEARTBEAT` (connection.cpp:205) and no `@source_heartbeat_period` is set (grep: no heartbeat/replica_uuid anywhere in src). In blocking (pull) mode an idle source and a silently partitioned source are indistinguishable: both end after `connection.read_timeout` (README:377, 719). No setting is validated (connection_config.cpp:47-59 checks only host/port vs dns_srv_name), so `read_timeout: 0` is passed through to `MYSQL_OPT_READ_TIMEOUT` (connection.cpp:302) — semantics of 0 are libmysqlclient's (likely "no timeout" => a partition hangs pull, and SIGTERM cannot be honoured because the jthread join waits on the blocked read; README:719).
3. **No `@replica_uuid`, `server_id` unvalidated.** `server_id` is a raw uint32 (replication_config.hpp:33, validate() at replication_config.cpp:26 does not check it). Since PBS sets no replica UUID, the source's zombie-dump-thread killing is keyed on server_id: two PBS instances (or PBS and a real replica) with the same server_id should evict each other's dump thread on each reconnect → CR_SERVER_LOST → idle → reconnect ping-pong. Not verified; good Antithesis scenario.
4. **Ticket 23 confirmed in code.** `process_connection_config`/`process_ssl_config` set SSL mode/CA/…/TLS and the three timeouts only (connection.cpp:225-321); `MYSQL_OPT_GET_SERVER_PUBLIC_KEY`/`MYSQL_SERVER_PUBLIC_KEY` are never set. With `ssl.mode=disabled` a caching_sha2_password user cannot do full auth. Implication for the harness: on MySQL 9.x (no mysql_native_password) connections must use TLS (`preferred` or stronger) or pre-warm the auth cache.
5. **Version-specific parsing.** Supported event layouts are 8.0 (80000) and ≥8.3 tagged-GTID (80300) (events/protocol_traits_fwd.hpp:30-37); anything ≥8.3 (8.4, 9.x) is parsed with the 8.3 table (reader_context.cpp:112, 472). FDE server version greater than `mysql_get_server_version()` is a fatal `logic_error` (reader_context.cpp:646-651); FDE post-header lengths are validated against the hard-coded table (654-657), so a future 9.x that adds an event type is a fatal error, not a skip. Ticket 1 (unparsable version string) lives on this path (not re-verified by me).
6. **Connection/thread hygiene.** `mysql_library_init` once per `library` (library.cpp:33); connections are created on the collector jthread with no explicit `mysql_thread_init/end` (relies on implicit init). `MYSQL_OPT_RECONNECT` is not used (good: no silent mid-dump reconnect). `connection::operator=` swap ordering is handled deliberately (connection.cpp:370-383). `max_allowed_packet` is not set on the client side (see Open questions).

### B. AWS SDK C++ S3 CRT client (binsrv/s3_storage_backend.cpp)

7. **Ticket 16 confirmed (mechanism).** `aws_context` default-constructs `Aws::S3Crt::ClientConfiguration configuration_{}` (s3_storage_backend.cpp:193-196); nothing sets `disableIMDS`, `shouldDisableIMDS`, timeouts, or retry strategy anywhere in the file. In an Antithesis network with no 169.254.169.254, every backend construction (every `binlog_server` invocation and every restart) pays the IMDS timeout unless the container sets `AWS_EC2_METADATA_DISABLED=true`. Decide deliberately: setting it hides ticket 16 but keeps restarts fast.
8. **All timeouts/retries are SDK/CRT defaults.** No `requestTimeoutMs`, `connectTimeoutMs`, `retryStrategy`, part size or throughput target is configured. QA measured that single PUT failures are retried transparently and six consecutive 500s exceed the retries (ticket 18). A hung S3 endpoint therefore blocks for whatever the CRT default is — unbounded from PBS's point of view.
9. **S3 write is "rewrite the whole object" from a local temp file.** `do_write_data_to_stream` appends to a local temp file, `flush()`es, then `PutObject`s the entire file (s3_storage_backend.cpp:850-863, 933-938); append-mode open first downloads the whole object (829-831); `do_resize_object` downloads, truncates locally, re-uploads (765-808). Consequences: (a) ticket 17's quadratic upload (partly documented at README:671); (b) the S3 backend depends on the *local* filesystem (`fs_buffer_directory` or `/tmp/<uuid>`, 559-590) — ENOSPC there fails S3 writes; (c) PutObject replaces atomically, so a crash mid-upload leaves the previous object version (object PUT precedes metadata PUT in `storage_core::write_event_block`, storage_core.cpp:307-321, so object size ≥ metadata size after a crash, which startup truncation handles).
10. **Temp files leak on crash.** Temp copies (full binlog size) are removed only in `close_stream_internal`/destructor (940-946, 640-651). After SIGKILL the `/tmp/<uuid>` dir or the files inside a configured `fs_buffer_directory` are never reclaimed (fresh UUID names every run, 929-931). Repeated crash/restart cycles grow local disk use by up to one binlog per crash.
11. **Sync S3 I/O under the storage lock blocks the replication-source thread.** `write_event_block` holds `unique_lock mutex_` across the data PUT and metadata PUT (storage_core.cpp:305-321). The sender's `fetch_event_block` takes `shared_lock` and does a ranged GetObject (461, 542) **on the single Boost.Asio thread** (network_service.cpp:301-308; io_ctx.run() in pull_operation.cpp:160). A slow/retrying S3 PUT therefore stalls every replica session, the acceptor, and the SIGINT/SIGTERM handler (registered on the same io_ctx, pull_operation.cpp:99-104). Same applies, more mildly, to slow local disk.
12. **Credentials and addressing.** Credentials come only from the URI; empty user/password become an explicit empty `AWSCredentials` (97-112, 194-195), so the SDK default chain (env, instance profile) is not consulted. Endpoint URIs force path-style (`useVirtualAddressing=false`, 252) and default region us-east-1; `s3://bucket/...` without region does a GetBucketLocation with a throwaway client (210-226). There is no CA-file option, so HTTPS to a self-signed MinIO needs the CA in the system store. `Aws::InitAPI`/`ShutdownAPI` run per `aws_context` (78-83).
13. **`do_fsync` is a no-op on S3** relying on S3 read-after-write consistency (815-819) — the S3 stand-in must provide strong consistency for overwrite+read (MinIO and Versity do).

### C. Local filesystem

14. **Ticket 19 confirmed.** Binlog data goes through `std::ofstream::write+flush` with an explicit TODO to fsync (filesystem_storage_backend.cpp:216-231); `do_close_stream` only closes (233-236). Metadata/index use tmp+fsync+rename+dir-fsync (127-160). Resize fsyncs the file but not the directory (162-172); `remove_object` defers to `do_fsync()` of the root dir (174-194, basic_storage_backend.cpp:53-74). New binlog file creation (`open_stream` create mode) does not fsync the directory. `util::fsync` reopens the path `O_RDONLY` and fsyncs (native_file_operations_helpers_posix.cpp:33-55) — on Linux this flushes the inode but may not surface writeback errors that occurred before the reopen. Antithesis container kills keep the page cache, so ticket 19 is likely reachable only with a whole-VM/node crash.
15. `do_list_objects` throws if any non-regular file is in the storage dir (106-112) — a stray directory (e.g. created by an operator or by a misconfigured `fs_buffer_directory` pointing inside the storage) makes every mode fail.

### D. Boost.Asio replication source (src/minimysql)

16. **Listener dies permanently on unexpected accept errors.** Any accept error other than `operation_aborted`/`bad_descriptor` is rethrown, caught by `handle_exception`, and the listener coroutine ends (network_service.cpp:643-668). The collector keeps running, so `pull` stays up while the replication source is silently dead. There is no connection cap, so fd exhaustion (EMFILE from many replica connections, plus S3 temp files) is a plausible trigger. Plain TCP only, IPv4 any-address (680-681), no TLS.
17. Per-frame read/write timeouts use a `steady_timer` race (network_io_operations.cpp:51-190); timeouts and EOF/RESET are logged at info and end only that session (network_service.cpp:236-276). The blocking dump polls storage every 500 ms (294, 318-320) and sends no heartbeats (ticket 20 context).

### E. OpenSSL

18. Used for binlog encryption (EVP cipher/digest wrappers, opensslpp/*), RNG for the auth scramble (`RAND_bytes`, crypto_rng.cpp:41; connection_context.cpp:491-503). Errors drain the OpenSSL error queue into `core_error` (opensslpp/core_error.cpp:32-66). Only a `file://` keyring exists (keyring_factory.cpp:31-44) — no network KMS dependency. libmysqlclient brings its own OpenSSL use for TLS.

### Antithesis stand-ins needed
- Real `mysqld` containers (8.0, 8.4, 9.x) with binlog + GTID; TLS enabled (finding 4); distinct server_ids.
- S3: MinIO or Versity S3 Gateway container, endpoint-form URI `http://key:secret@s3:9000/bucket/path`; decide on `AWS_EC2_METADATA_DISABLED`.
- Writable local volume for storage and for `fs_buffer_directory`.
- Replica/client container (mysqlbinlog `--read-from-remote-server`) for the pull source.

## Assumptions
- libmysqlclient maps read timeouts and socket resets to CR_SERVER_LOST (consistent with QA's toxiproxy results that pull survives resets/stalls); not checked in libmysqlclient source.
- Graceful source shutdown is survived by pull (MTR pull_mode.test restarts the server); the exact error code seen was not checked.
- Ticket 16/17/18 measurements taken as leads; I confirmed mechanisms (code), not timings.
