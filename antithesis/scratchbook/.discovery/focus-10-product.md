# Focus 10: Product context (binlog_server @ 99de682)

## Findings

### F1. What the product is (correcting the brief)
`binlog_server` is a replication client that copies a MySQL source's binlogs into a storage (`file://` or S3/MinIO), optionally encrypted (`storage.encryption`) or re-split (`replication.rewrite`, GTID mode only). It runs as a one-shot or long-lived CLI process, not as a daemon cluster. README.md:1-5, :145-175. Packaging installs only the binary and `/etc/percona-binlog-server/main_config.json` (packaging/rpm/binlog-server.spec:143-146). There is no systemd unit, so restarts and scheduling (cron `fetch`, supervised `pull`) are left to the operator.

- `pull` is not only "serve to replicas". It runs both halves in one process. A collector thread keeps reconnecting to the source (src/operations/pull_operation.cpp:121-152), and a `minimysql::network_service` on `replication_source.port` serves stored binlogs to downstream clients via COM_BINLOG_DUMP / COM_BINLOG_DUMP_GTID (pull_operation.cpp:111-112; src/minimysql/connection_context.cpp:431,446). Only `pull` mode has a replication source; `fetch` has none.
- For **encrypted** storages, the replication source is the only way inside the product to read the plaintext back. Decryption happens on the read path (src/binsrv/storage_core.cpp:544-557), and no CLI mode decrypts or exports. Restoring from an encrypted backup therefore depends on `pull` + `mysqlbinlog --read-from-remote-server` (with `--raw` to copy) or a replica. That raises the severity of every sender-side bug on encrypted storages.

### F2. Critical workflows and what a user-visible failure is

| # | Workflow | Entry | User-visible failure (oracle) | Cost |
|---|---|---|---|---|
| W1 | Continuous backup for PITR: `pull` (or repeated `fetch`) into storage | collector_context.cpp:125-205 | Storage is **not a byte prefix** of the source's binlogs as sent. A stored or indexed binlog is missing, duplicated or reordered. A GTID that is in `added_gtids` is missing from the bytes. The metadata `size` is not at a transaction boundary. A run exits 0 while the storage diverges from the source | **Catastrophic** (silent, found only at restore) |
| W2 | Resume after stop/crash ("Running the utility for the second time ... resum[es] streaming from the position at which the previous run finished", README.md:709-711) | storage open + `open_connection_and_switch_to_replication` (collector_context.cpp:207-271) | After restart, the storage **cannot be opened** (wedged; the operator must wipe it), data is duplicated or skipped, or the process never catches up to an exact copy | Severe. A wedge is loud but stops backups. Duplicates or gaps are silent |
| W3 | Graceful stop (SIGINT/SIGTERM): "leaving storage in consistent state" (README.md:713-721) | pull_operation.cpp:96-101; storage dtor flushes (storage.cpp:68-77) | Exit code is not 0 after a signal, shutdown takes longer than `read_timeout`+1 s, or data received before the signal is lost | Medium |
| W4 | Hard kill (`kill -9`) "may result in losing some progress" (README.md:721) | n/a | Losing data that was **not yet checkpointed** is *allowed*. Not allowed: storage not reopenable, non-prefix bytes, a metadata size past the file or off a transaction boundary | Severe if the storage wedges or corrupts |
| W5 | Serve stored binlogs (restore / replica / `mysqlbinlog --raw`) via `pull`'s replication source | sender_context.cpp:56-140 (event sequence contract in comments) | The client receives events not equal to the stored (decrypted) bytes, wrong artificial ROTATE/FDE, gaps or duplicates across file boundaries, a disconnect on a valid request, or a hang | Severe for encrypted storages (only restore path), high otherwise |
| W6 | PITR planning: `search_by_timestamp`, `search_by_gtid_set` | search_helpers.cpp:30-84 | GTID search: the returned files do not cover the requested set, it reports "cannot be covered" when the storage does cover it, or the files are not in index order. Timestamp search: it omits a file holding an event ≤ ts, or the JSON `status` is wrong | **High and silent**. A PITR tool replays the wrong files and the restore is short |
| W7 | Retention: `purge_binlogs <name>` | purge_binlogs_operation.cpp:46-86 | It deletes more than `seq ≤ target`, deletes the tail, returns `success` when files are left orphaned (it should return `warning`, README.md:440-473), or the storage cannot be resumed afterwards | High. Over-deletion is irreversible |
| W8 | Inventory: `list` | list_operation.cpp | The listing disagrees with the stored objects (names, sizes, GTIDs, timestamps) | Medium. It feeds W6/W7 decisions |

Ranking for the workload's oracle budget: W1 ≈ W6 (silent wrong backup or wrong restore set) > W2/W4 (wedge or corruption after a fault) > W5 > W7 > W3 > W8 > performance (S3 re-upload amplification is documented as expected, README.md:670-671).

### F3. Concrete product contracts the workload can assert (claimed, not verified)
1. **Prefix and exact copy.** The QA harness already encodes the product's correctness notion. `storage_holds_prefixes` and `check_complete_copy` (extra/qa/fetch_crash_test.py:636-697) compare the stored file to `binlog_as_sent()` (with the IN_USE flag cleared and the checksum recomputed). Their rules: index names are a prefix of the server's binlog list, the metadata `size` is at or below the file length and at a transaction boundary, and a complete fetch ends as an exact copy, except that the tail may hold only the magic when it has no transactions. Reuse these as the Antithesis oracles for W1/W2/W4. Byte comparison does not apply with `rewrite` or `encryption`. For those, compare the event stream (GTIDs and payloads) read back through W5.
2. **Transaction-boundary persistence.** `flush_event_buffer_internal` writes only up to `last_transaction_boundary_position_in_event_buffer_` (src/binsrv/storage.cpp:276-302). On a read timeout the collector discards the incomplete tail before flushing (collector_context.cpp:189-201). Invariant: the persisted size is always at a transaction boundary.
3. **Exit-code contract.** `fetch` exits 0 only when it reaches EOF (fetch_operation.cpp:107-115). `pull` exits 0 only after a signal (pull_operation.cpp:160-164). Each query mode prints exactly one JSON object with `status` ∈ {success, warning, error} and exits non-zero only on error (purge_binlogs_operation.cpp:79-86). A workload can check "exit 0 ⇒ storage consistent with source" (ticket 25's silent case violates this).
4. **Purge safety.** The tail cannot be purged ("at least one binlog file must remain ... to preserve the resume position", README.md:420-424). Purge while `fetch`/`pull` runs is **documented as unsupported** ("may cause data corruption and should be avoided", README.md:475). A workload must not count corruption from concurrent purge as a bug unless the product claims otherwise. Ticket 9 argues the result should at least not wedge. Treat that as a design question, not a property.
5. **Pull keeps reconnecting.** "Any network-related error ... does not result in immediate termination ... More serious errors (like out of space) cause program termination" (README.md:375-378). This is a liveness property: after a partition heals, `pull` resumes and converges to an exact copy.

### F4. Doc-vs-code gap worth a property (partially validated)
`connection::fetch_binlog_event` swallows only `CR_SERVER_LOST`. Every other client error raises `core_error` (src/easymysql/connection.cpp:544-551). In `pull`, that exception leaves the collector thread and terminates the process (pull_operation.cpp:149-157). Connect and switch failures, by contrast, return `false` and retry (collector_context.cpp:209-216, 263-266). So a mid-stream network fault that libmysqlclient reports as anything other than 2013 (for example 2006, or a source-side 1236) ends `pull`. The README promises it would reconnect. I have not determined which errno values the network faults Antithesis injects (resets, partitions) actually produce. The property "pull survives any network fault and converges" would settle it.

## Assumptions
- Users consume backups in one of three ways: copying `file://` / S3 objects directly into `mysqlbinlog` (unencrypted, no rewrite), streaming through `pull`'s replication source, or using the `search_*` JSON to select which object URIs to fetch.
- "Source" means one MySQL server with stable identity, except in scenarios that deliberately test failover (ticket 25).
- An Antithesis workload controls the MySQL source and can compute `binlog_as_sent()` as the existing QA harness does.
