        Ticket 1 · Bug · binsrv/events

        FORMAT_DESCRIPTION event with an unparsable server version terminates the utility

        StatusOpen
PriorityHigh
Componentbinsrv/events

      Copy summaryCopy description

      Summary

      generic_post_header_impl<code_type::format_description>::get_encoded_server_version() is declared noexcept, but it parses the server version string received from the network with util::semantic_version, which throws std::invalid_argument on anything that isn't major.minor.patch (an optional -suffix is stripped first). An exception escaping a noexcept function calls std::terminate, so the whole process aborts.

      Where it happens

        The FORMAT_DESCRIPTION post header parser calls it while parsing (format_description_post_header_impl.cpp:130).

        reader_context calls it when processing the event (reader_context.cpp:646), reached from collector_context.cpp:442 for every received event.

        calculate_encoded_size() (also noexcept), encode_to() and operator<< call it too.

      Reproduction

      Parse a FORMAT_DESCRIPTION event whose server version field is one of:

        8.0.36_custom: terminates (server_version "patch" component is not a numeric value)

        8.0.300: terminates (the patch value overflows uint8)

        8.0.36.1: terminates (server_version has more than 3 components)

        8.0.36-28 (Percona Server style): parsed, because the suffix is stripped

      User impact

        fetch and pull abort mid-stream with SIGABRT: no graceful shutdown, no final flush of buffered events.

        Combined with ticket 2, everything received for the current binlog since the last rotation is lost.

        Can be triggered by any source whose version string is not strictly numeric, or by a malicious or broken peer.

      Expected behaviour

      An unparsable server version is rejected with std::invalid_argument, and the utility exits with its normal error handling (exit code 1).

      Suggested fix

      Parse and validate the version once in the constructor that reads the event (throwing std::invalid_argument there) and store the encoded value, so the accessors really cannot throw. At minimum, remove noexcept from get_encoded_server_version() and calculate_encoded_size().

      Tests

        MTR: binlog_streaming.fde_invalid_server_version patches the server version in a closed binlog on the source server and expects fetch to exit with 1. Today the utility aborts (exit 134).

        Property tests (tests/event_property_test.cpp): EventParsingOfCorruptedEventsFailsCleanly, EventPrintingOfCorruptedEventsFailsCleanly.

      Verified by a standalone program built from the project sources (Homebrew LLVM 21, Boost 1.90). Confirmed on Linux (Ubuntu 24.04, GCC 14): the event property test aborts with this exception under ASAN, and the MTR test fde_invalid_server_version fails on MySQL 8.0.45 and 8.4.8 with terminate called … server_version "patch" component is not a numeric value and exit code 134. Still open on upstream main @ ee82afa.

        Ticket 2 · Bug · regression · binsrv/storage

        Storage checkpointing settings are ignored

        StatusFixed upstream in 3804c25 (PS-69, #198)
PriorityHigh
Componentbinsrv/storage
Introduced in7f8cb69 (#189)

      Copy summaryCopy description

      Summary

      storage.checkpoint_size and storage.checkpoint_interval have no effect. binsrv::storage never copies them from the configuration into checkpoint_size_bytes_ and checkpoint_interval_seconds_, which keep their default value of zero. So size_checkpointing_enabled() and interval_checkpointing_enabled() (storage.hpp:148-155) always return false, and the flush check in storage::write_event() (storage.cpp:170-185) never fires.

      Cause

      Commit 7f8cb69 ("Rework storage layer abstractions to support simultaneous reads and writes (part 2)", #189) moved the constructor logic into storage_core::storage_core but dropped this block. The checkpoint fields stayed in storage:

const auto &checkpoint_size_opt{storage_config.get<"checkpoint_size">()};
if (checkpoint_size_opt.has_value()) {
  checkpoint_size_bytes_ = checkpoint_size_opt->get_value();
}
const auto &checkpoint_interval_opt{storage_config.get<"checkpoint_interval">()};
if (checkpoint_interval_opt.has_value()) {
  checkpoint_interval_seconds_ =
      std::chrono::seconds{checkpoint_interval_opt->get_value()};
}

      User impact

        Data reaches the storage backend only when a binlog file is closed (rotation) or the utility shuts down.

        S3 storage keeps each whole binlog file in memory until rotation.

        After a crash or kill -9, the whole current binlog is lost, not just the data since the last checkpoint.

        In pull mode, replicas connected through COM_BINLOG_DUMP cannot see the current binlog until it rotates.

        The startup log still prints the configured values (logger_helpers.cpp:190-193), so the problem is invisible.

      Why tests did not catch it

      mtr/binlog_streaming/t/checkpointing.test sets the options, runs fetch and checks only the final result, which is the same with or without checkpoints.

      Expected behaviour

      With checkpoint_size = S, committed data not yet on the backend never exceeds about S plus one transaction. With checkpoint_interval = T, buffered complete transactions are flushed on the first event after T has passed.

      Suggested fix

        Restore the block above in storage::storage (storage.cpp:47), reading config.root().get<"storage">().

        Extend checkpointing.test to check that the current binlog grows on the backend before rotation.

      Resolution

      Fixed upstream in 3804c25 ("PS-69 fix: Storage checkpointing settings are ignored (#198)"), which restores the block above in the storage constructor.

      Tests

        tests/storage_property_test.cpp: StorageRespectsCheckpointSize requires that complete transactions not yet on disk stay below checkpoint_size. It failed on every run before the fix (shrinking to a single 64-byte transaction with checkpoint_size 64) and passes after it.

        extra/qa/repro_broken_checkpointing.py runs pull against a source and compares the source position with the on-disk file size (not run against a server).

        checkpointing.test still checks only the final result; extending it to check for flushes before rotation is still worth doing.

      Verified by the storage property test, failing before the fix and passing after it, on macOS (Homebrew LLVM 21) and on Linux (GCC 14, debug and ASAN builds).

        Ticket 3 · Bug · binsrv/gtids

        gtid_set does not validate GNO bounds (parser overflow, interval bounds, binary decoder)

        StatusOpen
PriorityMedium
Componentbinsrv/gtids

      Copy summaryCopy description

      Summary

      binsrv::gtids::gtid_set accepts GNOs outside the valid range [1, 9223372036854775807] (INT64_MAX, as in MySQL Server) in several places, and can end up holding values it cannot print and parse back.

      Issues

        GNO overflow in the text parser. parse_gno() has no overflow check (see its // TODO: add overflow checks), so values wrap: uuid:100000000000000000000 becomes GNO 7766279631452241920, and uuid:18446744073709551617 (2^64 + 1) becomes GNO 1.

        add_interval() doesn't check the upper bound. Only the lower bound is validated. add_interval(u, tag, 1, 9223372036854775808) is accepted. With UINT64_MAX, upper + 1 wraps to 0 and leaves an empty entry, so is_empty() returns false for a set with no GTIDs.

        subtract_interval() with an upper bound of UINT64_MAX removes nothing, because of the same wraparound. It's public API, though nothing in production calls it.

        The binary decoder accepts sets it can't represent as text. process_intervals() only checks upper <= lower. A TSID with zero ranges (the entry is created before ranges are read), a nil UUID, or a range starting at GNO 0 is accepted, and the resulting str() fails to parse back (cannot parse GTID set).

      User impact

        search_by_gtid_set gives wrong answers instead of a parse error. Searching for <server_uuid>:18446744073709551617 succeeds and returns the binlog containing GNO 1.

        GTID sets are persisted in storage metadata as text (boost::lexical_cast through operator<< and operator>>). A set that cannot be parsed back from its own text could make the storage unreadable on the next start.

      Expected behaviour

        Text parsing rejects any GNO outside [1, max_gno], including values that overflow 64 bits, with std::invalid_argument.

        add_interval() validates both bounds.

        subtract_interval() handles UINT64_MAX without wrapping around, either by rejecting it or by clamping it to max_gno.

        The binary decoder rejects zero-range TSIDs, nil UUIDs and ranges outside [1, max_gno + 1).

      Tests

        Property tests (tests/gtid_set_property_test.cpp, -DWITH_PROPERTY_TESTS=ON): GtidSetParseRejectsOutOfRangeGno, GtidSetAddIntervalRejectsOutOfRangeUpperBound, GtidSetSubtractIntervalBeyondMaxGnoRemovesTail, GtidSetDecodedFromBinaryIsPrintable.

        MTR: binlog_streaming.search_by_gtid_set_gno_range covers issues 1 and 2 through the command line.

      Verified by property tests and standalone programs (Homebrew LLVM 21, Boost 1.90) and by reading the code. Confirmed on Linux (Ubuntu 24.04, GCC 14, debug and ASAN builds) with the same four failing properties. The MTR test search_by_gtid_set_gno_range fails on MySQL 8.0.45 and 8.4.8 at case 4: <server_uuid>:18446744073709551617 is accepted and the command exits 0. Still open on upstream main @ ee82afa.

        Ticket 4 · Bug · build platform

        Boost.ICL interval sets give wrong results with Apple clang and system libc++

        StatusOpen
PriorityMedium
Componentbuild, binsrv/gtids

      Copy summaryCopy description

      Summary

      Built with Apple clang 21 (clang-2100.3.34.2) and Apple's system libc++, boost::icl::interval_set<std::uint64_t> (Boost 1.90, default std::set backend) merges and subtracts ranges incorrectly. gtid_set is built on it, so GTID sets are wrong in these builds.

      Reproduction (Boost.ICL only)

#include <cstdint>
#include <iostream>
#include <boost/icl/interval_set.hpp>
int main() {
  using icl_set = boost::icl::interval_set<std::uint64_t>;
  using iv = icl_set::interval_type;
  icl_set s;
  s += iv::right_open(3, 4); s += iv::right_open(1, 2); s += iv::right_open(1, 4);
  std::cout << boost::icl::interval_count(s) << " (expected 1)\n";
}

        Apple clang with system libc++ prints 2, with -std=c++17, c++20 and c++23, at -O0 and -O1.

        Subtracting [1, 4) from {[1, 2), [3, 4)} leaves [3, 4).

        Homebrew LLVM 21 with its own libc++ prints 1 (correct).

        Apple clang with -DICL_USE_BOOST_MOVE_IMPLEMENTATION prints 1 (correct).

      Effect on gtid_set

        Adding 3, then 1, then the range 1-3 gives uuid:1:1-3, which is not equal to its own parsed text.

        {1, 3} minus the range 1-3 leaves {3}.

      Notes

      Apple clang isn't in the README's supported toolchains (clang 15–20, gcc 12–14), but CMakeLists.txt sets up macOS builds and defaults to libc++ on Darwin. Linux with GCC 14 and libstdc++ is not affected: the model-based properties pass there in debug and ASAN builds. The clang20 presets (libc++) have not been checked.

      Suggested fix

      Define ICL_USE_BOOST_MOVE_IMPLEMENTATION for all targets using Boost.ICL, so ICL uses its boost::container backend on every toolchain. Optionally report upstream.

      Tests

      The model-based properties in tests/gtid_set_property_test.cpp catch this in about 4 of 5 fresh runs at the default 100 cases: GtidSetOperationsMatchModel, GtidSetUnionMatchesModel, GtidSetDifferenceMatchesModel, GtidSetLexicalCastRoundTrip.

      Verified on macOS with Apple clang 21 and system libc++. Correct with Homebrew LLVM 21 and with Linux GCC 14.

        Ticket 5 · Bug · binsrv/events, binsrv/gtids

        Oversized GTID tag in event data is reported as bad_alloc

        StatusOpen
PriorityLow
Componentbinsrv/events, binsrv/gtids

      Copy summaryCopy description

      Summary

      Two parsers use a tag length read from the wire to resize fixed 32-byte storage (tag_storage, a boost::container::static_vector<std::byte, 32>) without checking it. For lengths above 32, resize() throws boost::container::bad_alloc instead of the parsers' usual "invalid data" error:

        the GTID_TAGGED_LOG body parser (gtid_tagged_log_body_impl.cpp, field_id_type::tag in process_field_data());

        the GTID set binary decoder (gtid_set.cpp, tag_parser), used for tagged PREVIOUS_GTIDS_LOG bodies.

      Where it happens

        Case 1: any fetch or pull receiving the event, because reader_context parses the body (reader_context.cpp:978).

        Case 2: when events are logged at debug level or lower, because the collector builds and prints every event (collector_context.cpp:458), which decodes the GTID set.

      Current and expected behaviour

        Current: fetch exits with 1 and logs std::exception caught: boost::container::bad_alloc thrown, which points at an out-of-memory condition rather than corrupted input. boost::container::bad_alloc does not derive from std::bad_alloc.

        Expected: check the length against tag_max_length (32) before resizing and raise std::invalid_argument with a clear message, like the other length checks in these parsers.

      Tests

        Property tests (tests/event_property_test.cpp): EventParsingOfCorruptedEventsFailsCleanly, EventPrintingOfCorruptedEventsFailsCleanly.

        MTR (8.4 only): binlog_streaming.gtid_tagged_log_oversized_tag and binlog_streaming.previous_gtids_log_oversized_tag patch the tag length in a closed binlog on the source server and assert that the utility log contains no bad_alloc.

      Verified by property tests, and by patching a binlog file generated with the project's own encoder and parsing it with the project's parser. Both MTR tests fail as expected on MySQL 8.4.8 (fetch exits with 1, but the utility log contains bad_alloc) and are skipped on 8.0.45. Still open on upstream main @ ee82afa.

        Ticket 6 · Bug · binsrv/storage

        Closing a binlog in the middle of a transaction leaves stale timestamps in storage

        StatusOpen
PriorityLow
Componentbinsrv/storage

      Copy summaryCopy description

      Summary

      storage::close_binlog() (storage.cpp:188) drops the events of an incomplete transaction (event_buffer_.clear()) but not their timestamps: incomplete_transaction_timestamps_ keeps them. storage::open_binlog() asserts that this range is empty (storage.cpp:122).

      Behaviour

        Debug builds: close_binlog() followed by open_binlog() with an incomplete transaction still buffered aborts on the assertion.

        Release builds (NDEBUG): the stale timestamps are carried into the next binlog. They are added to the first complete transaction written there and end up in that binlog's metadata.

      Reproduction (release build)

        Open binlog.000001 and write one event with timestamp 1000 that is not at a transaction boundary.

        close_binlog(), then open binlog.000002.

        Write one complete transaction with timestamp 5000, then close_binlog().

      The record of binlog.000002 has timestamps min=1000 max=5000; expected min=5000 max=5000.

      Impact

      Latent today. The collector only closes a binlog at a transaction boundary (ROTATE / STOP events) or after calling discard_incomplete_transaction_events() on a disconnect (collector_context.cpp:195). If a future caller closes a binlog mid-transaction, binlog timestamp ranges would be wrong, and search_by_timestamp uses them to pick binlog files.

      Suggested fix

      Make close_binlog() leave no incomplete-transaction state behind: clear incomplete_transaction_timestamps_ (and reset incomplete_transaction_last_sequence_number_ to ready_to_flush_last_sequence_number_), as discard_incomplete_transaction_events() does. Alternatively, document and enforce that callers must discard first.

      Tests

      tests/storage_property_test.cpp (StorageMatchesModel) found it by rotating a binlog while a transaction was incomplete. The test currently discards before rotating, like the collector; after the fix, that discard can be removed so the property covers this case.

      Verified with a standalone program linking the project's storage code, with storage.cpp built with NDEBUG (Homebrew LLVM 21). close_binlog() is unchanged on upstream main @ ee82afa.

        Ticket 7 · Bug · binsrv/storage (replication source)

        indexed_event_block loops forever on an event size field below the common header size

        StatusOpen
PriorityMedium
Componentbinsrv (indexed_event_block), COM_BINLOG_DUMP

      Copy summaryCopy description

      Summary

      The binsrv::indexed_event_block constructor splits a block of bytes read from a binlog file into events, using the event_size field of each common header. It does not check that the size is at least the common header size (19 bytes); it only asserts it (indexed_event_block.cpp:43) and then advances by that size.

      Behaviour

        Debug builds: the assertion aborts the process.

        Release builds (NDEBUG, which the release_* presets define): the loop never ends and keeps adding index records until memory runs out. With a size of 0 the offset never advances. With a size between 1 and 18 the loop lands in the middle of an event, where it typically reads a size of 0 and stops advancing.

      Reproduction (release build)

      A 38-byte buffer holding two events with type code 2 (query), the second one with event_size 19:

        first event event_size 19: both events indexed, actual size 38 (correct);

        first event event_size 5: still running after 10 s;

        first event event_size 0: still running after 10 s.

      Impact

      In pull mode, operations::sender_context uses indexed_event_block for every block it reads from storage to serve COM_BINLOG_DUMP. A single corrupted or garbage event_size field in a binlog file (for example after disk corruption or a damaged object in S3) hangs that replica's session, consuming CPU and memory without limit, instead of reporting a corrupt binlog.

      Expected behaviour

      An event size smaller than the common header size is treated as invalid data: the constructor raises std::invalid_argument (or stops indexing and lets the caller report corruption), like the other checks on data read from storage.

      Suggested fix

      Replace the assertion at indexed_event_block.cpp:43 with a check that rejects event_size < events::common_header_view_base::size_in_bytes.

      Tests

        Property test tests/indexed_event_block_property_test.cpp (IndexedEventBlockIndexesOnlyCompleteEvents): for buffers built from event-like chunks (valid and invalid type codes, matching and mismatching size fields, trailing bytes), the indexer must either reject the input cleanly or index only complete events that match the bytes. It hits the assertion in every run.

        The read path as a whole is covered by StorageReadBackMatchesDisk in tests/storage_property_test.cpp, which passes.

      Verified on Linux (Ubuntu 24.04, GCC 14): the property test with the debug_gcc14 preset, and the release behaviour with a standalone program built with -DNDEBUG.

        Ticket 8 · Bug · opensslpp (binlog encryption)

        cipher_context::create_with_offset() does not carry the CTR counter into the upper half of the IV

        StatusOpen
PriorityLow
Componentopensslpp, binsrv/storage (encryption)

      Copy summaryCopy description

      Summary

      opensslpp::cipher_context::create_with_offset() starts an AES-CTR key stream in the middle of a binlog file. It treats only the last 8 bytes of the 16-byte IV as the counter and adds offset / 16 to them as a 64-bit value, with no carry into the first 8 bytes (cipher_context.cpp, counter += offset / block_size). OpenSSL's CTR mode increments the whole 128-bit IV, so when the last 8 bytes overflow, the two produce different key streams.

      Reproduction

      OpenSSL's own CTR mode carries. Key 000102030405060708090a0b0c0d0e0f, IV 0000000000000000ffffffffffffffff, 32 zero bytes encrypted with openssl enc -aes-128-ctr:

        second block: 13189a6ae4ab07ae70a3aabd30be99de;

        AES-ECB of counter 00000000000000010000000000000000 (with carry): 13189a6ae4ab07ae70a3aabd30be99de, a match;

        AES-ECB of counter 00000000000000000000000000000000 (no carry, what create_with_offset() computes): c6a13b37878f5b826f4f8162a1c8d879.

      The property test finds it in every run, shrinking to cases such as IV 0000000000000000ffffffffffff3bc9 at offset 1099511627544.

      Impact

      Storage encrypts with create_with_offset() for writes and reads at non-zero offsets, but a single write or read is processed by OpenSSL, which carries within it. If a binlog file's counter crosses the 64-bit limit inside one write, the data after the crossing is encrypted with the carried counter, while a later read starting after the crossing uses the non-carried one and returns garbage. External tools that decrypt the file sequentially would disagree in the same way.

      The IV is random for every file, so this needs the last 8 bytes of the IV to be within the file's length (in 16-byte blocks) of 264: about a 1 in 238 chance for a 1 GB file. Rare, but silent data corruption when it happens.

      Suggested fix

      Add offset / block_size to the IV as a 128-bit big-endian number, carrying from the last 8 bytes into the first 8.

      Tests

        tests/cipher_context_property_test.cpp: CipherContextOffsetMatchesCounterReference compares create_with_offset() with an independent reference (AES-ECB of a 128-bit counter) for generated IVs and offsets. It fails in every run today.

        The same file checks that encrypting in pieces equals encrypting in one call, and that decrypting from offsets round-trips (both pass), and tests/storage_property_test.cpp now also runs on encrypted storage.

      Verified on Linux (Ubuntu 24.04, GCC 14, OpenSSL 3.0.13) with the property test, and with the openssl command-line tool for OpenSSL's own carry behaviour.

        Ticket 9 · Bug · binsrv/storage

        Running purge_binlogs while fetch / pull is running leaves a storage that cannot be opened

        StatusOpen
PriorityHigh
Componentbinsrv/storage (filesystem and S3 backends), purge_binlogs

      Copy summaryCopy description

      Summary

      A streaming storage (fetch / pull) loads binlog.index only once, when it is created (storage_core.cpp:214), and keeps the list of binlogs in memory. purge_binlogs runs as a separate process: it rewrites binlog.index without the purged binlogs and deletes their data and metadata files. Nothing tells the running process about it. When the running process next creates a binlog (on rotation), it rewrites binlog.index from its stale in-memory list (storage_core.cpp:692), adding the purged binlogs back.

      The logic is in storage_core, shared by both storage backends, and the bug reproduces the same way on the filesystem and on S3.

      Reproduction

        A streaming storage holds binlog.000001 and binlog.000002.

        Another storage instance in purging mode (as purge_binlogs config.json binlog.000001 does) purges binlog.000001: the index now lists only binlog.000002 and the files are deleted.

        The streaming storage rotates to binlog.000003 and rewrites binlog.index with binlog.000001, binlog.000002 and binlog.000003.

        Opening the storage again fails with binlog index contains a reference to a non-existing object.

      Impact

        After an operator purges binlogs during normal operation, the next binlog rotation on the source makes the storage unopenable: binlog_server cannot be restarted (in any mode) until binlog.index is repaired by hand.

        The running process does not notice. In pull mode its binlog list still includes the deleted binlogs, so replicas reading from the beginning are directed to files that no longer exist.

        The README documents purge_binlogs as a normal operation and only forbids purging the binlog currently being written, so operators have no reason to stop fetch / pull first.

      Expected behaviour

      Purging while fetch / pull is running either works (the running process stops listing the purged binlogs and never writes them back to the index), or is refused with a clear error.

      Suggested fix

        Re-read binlog.index (or merge with it) in the streaming process before rewriting it, and drop purged binlogs from its in-memory list; or

        coordinate the two processes (for example a lock object in the storage that purge_binlogs must take, or a notification to the running process); or, at minimum,

        make purge_binlogs refuse to run while another process is streaming into the storage, and document that in the README.

      Tests

      tests/storage_property_test.cpp: StoragePurgeKeepsStorageReopenable purges generated prefixes of the binlogs through a second storage instance in purging mode, and after every operation requires a copy of the storage directory to open and hold exactly the remaining binlogs. It fails in every run today, shrinking to rotate, purge(1), rotate.

      The same property on the S3 backend (StoragePurgeKeepsStorageReopenableOnS3, run against an S3-compatible server) fails with the same error, binlog index contains a reference to a non-existing object, after 11 test cases. At the default 20 cases for S3 it can pass by chance: the filesystem run needed 67 cases.

      Verified on Linux (Ubuntu 24.04, GCC 14) with the property test. The two storage instances in the test share nothing but the files on disk, the same as separate pull and purge_binlogs processes. Confirmed on the S3 backend against Versity S3 Gateway 1.8.0 with StoragePurgeKeepsStorageReopenableOnS3 at 100 test cases. Open on upstream main @ ee82afa.

        Ticket 10 · Bug · minimysql (replication source)

        Binlog events of 16 MB or more cannot be sent to replicas in pull mode

        StatusOpen
PriorityHigh
Componentminimysql (connection_context, network_io_operations)

      Copy summaryCopy description

      Summary

      The MySQL protocol limits a packet payload to 0xFFFFFF (16,777,215) bytes: larger payloads are split into several packets, and a payload whose length is an exact multiple of 0xFFFFFF is followed by an empty packet. The replication source listener does neither:

        minimysql::connection_context::generate_encoded_binlog_event() always writes one packet with a 3-byte length of event size + 1 (the extra byte is the OK marker), so the length wraps around past 0xFFFFFF and no closing empty packet is sent;

        minimysql::async_write_mysql_frame() rejects any buffer of 16 MiB or more (frame payload size too large to send), so the session ends before such an event is sent.

      What the encoder produces

        event of 16,777,213 bytes: one packet, correct;

        event of 16,777,214 bytes: one packet of 0xFFFFFF bytes and no closing empty packet, so a client waits for a packet that never comes;

        event of 16,777,215 bytes: the header length is 0;

        event of 16,777,216 bytes: the header length is 1;

        event of 20,000,000 bytes: the header length is 3,222,785, and the rest of the event is read as further packets.

      Impact

      In pull mode, once a replica reaches a binlog event of about 16 MB or more (16,777,211 bytes, where the frame including its header reaches 16 MiB), the write is rejected and the session ends (confirmed end to end, see below). The replica reconnects, asks for the same position and fails again, so replication stops permanently at that event. MySQL allows events up to 1 GB (max_allowed_packet); a single row with a large LONGBLOB, LONGTEXT or JSON value produces such an event. The existing MTR test rs_large_event uses a 1.5 MB event, below the limit.

      Expected behaviour

      Events of any size up to the MySQL limit are sent as the MySQL server sends them: split into packets of at most 0xFFFFFF bytes with consecutive sequence numbers, followed by an empty packet when the payload length is an exact multiple of 0xFFFFFF.

      Suggested fix

        Split the payload in generate_encoded_binlog_event() (or in a shared helper used for all server packets) into packets of at most 0xFFFFFF bytes, adding the closing empty packet when needed.

        Let async_write_mysql_frame() send such multi-packet buffers instead of rejecting buffers of 16 MiB or more (limit by the configured maximum event size instead).

      Tests

        Ticket 14 · Bug · collector (GTID replication mode)

        Resuming in GTID mode after a binlog rotation loses the closing ROTATE event and skips binlogs without transactions

        StatusOpen
PriorityMedium
Componentoperations (collector_context), binsrv/storage

      Copy summaryCopy description

      Summary

      In GTID replication mode, the Binlog Server resumes streaming by sending its GTID set, and the source starts sending from the binlog that holds the first missing GTID. If the source rotated its binlog after the last transaction the Binlog Server received (FLUSH BINARY LOGS, a server restart, or reaching max_binlog_size), with no new transaction in the old binlog, the source starts from the new binlog. The ROTATE event that closes the old binlog on the source is never received. The storage then closes its copy of the old binlog without that event and opens the new one, so the stored copy ends before that event (44 bytes for a binlog named binlog.NNNNNN).

      If the source rotated more than once in that time, the binlogs in between hold no transactions and are never sent at all: the storage has no copy of them, and its binlog index jumps from the old binlog to the newest one.

      Position-based mode is not affected: it resumes at the stored binlog name and position, so the ROTATE event is received. Rewrite mode generates its own ROTATE events (collector_context.cpp:379). Plain GTID mode has nothing that fills the gap.

      Reproduction

        GTID mode: write a transaction on the source and run binlog_server fetch until it has caught up.

        On the source: FLUSH BINARY LOGS, then write another transaction.

        Run binlog_server fetch again.

        The stored binlog.000001 is 422 bytes; the source's closed binlog.000001 is 466 bytes: the same bytes followed by the ROTATE event.

      With a second FLUSH BINARY LOGS before the insert in step 2, the source has binlog.000001 to binlog.000003, and the storage holds only binlog.000001 (without its ROTATE event) and binlog.000003.

      Impact

        Stored binlogs are not exact copies of the source's binlogs, and binlogs without transactions can be missing from the storage. This happens in normal operation: whenever a periodic fetch or a reconnecting pull was caught up when the source rotated, which log rotation, backups and server restarts all do.

        In pull mode the replication source sends stored events as they are (sender_context does not create ROTATE events), so clients reading through pull do not receive the ROTATE that tells them the binlog file changed. Tools that rely on it, such as replicas tracking the source file name and mysqlbinlog --read-from-remote-server --raw naming its output files, are expected to be affected. This has not been confirmed end to end yet: mysqlbinlog --raw can read from pull since ticket 22 was fixed upstream, but this case has not been run against it; MySQL replicas still cannot connect to it (ticket 20).

      Expected behaviour

      The storage holds every binlog of the source since streaming started, each closed one ending with the ROTATE event that closes it on the source, as in position-based mode.

      Suggested fix

      When the first artificial ROTATE after a reconnect names a binlog other than the current stored one, close the current stored binlog with a ROTATE event naming the new binlog before opening it, as rewrite mode already does with generate_rotate_event(). The generated event should match the source's: timestamp, server ID, flags, the next-event position in the old binlog, and position 4 in its post header. Binlogs skipped in between can be created with their preamble and a ROTATE event, or the resume can request them by name and position. Whichever is chosen, the result should be byte-identical to the source's files.

      Tests

        MTR: binlog_streaming.gtid_resume_after_rotation (GTID mode) fetches, runs FLUSH BINARY LOGS twice and inserts a row, fetches again, and compares the stored first and second binlogs with the source's using diff_files. It fails on MySQL 8.0.45 and 8.4.8 today.

      Verified on Linux (Ubuntu 24.04, GCC 14, debug build) with the randomized crash test against MySQL 8.4.8, and with the MTR test on MySQL 8.0.45 and 8.4.8 (diff_files: the stored and server binlogs differ). Open on upstream main @ ee82afa.

Note that parts are not visible until the upload is completed, so readers (pull, the searches) and crash recovery need a design for the in-progress binlog, for example completing the upload at each checkpoint with UploadPartCopy of the existing object plus the new data.

        Alternatively, store each binlog as a series of objects (one per checkpoint) and join them on read or when the binlog is closed.

      storage::flush_event_buffer_internal() passes the buffered transactions to storage_core::write_event_block() and erases them from the buffer only after it returns (storage.cpp:276-302). write_event_block() appends the data to the binlog stream, then increases the binlog's size in memory, then saves the binlog metadata (storage_core.cpp:299-322). If any of these steps throws, the buffer keeps the data, and the next flush, normally the one in the storage destructor when fetch or pull exits after the error, writes the same data again.

      On S3 the stream is a local temporary file that is appended to and then uploaded whole, so the data is in the file even when the upload fails, and the second flush leaves it there twice:

        The binlog upload fails: the in-memory size was not increased, so the metadata saved by the second flush has the right size, while the object holds the new data twice. The next start truncates the last binlog to the metadata size, which removes the duplicate.

        The binlog upload succeeds but the metadata upload fails: the in-memory size was already increased, and the second flush increases it again. The object holds the new data twice and the metadata size matches it, so nothing on start detects or repairs it.

      Reproduction

      Position mode, S3 storage through a proxy that answers 500 InternalError to six consecutive PUT requests (more than the SDK's retries), MySQL 8.4.8 with small binlogs:

        Run fetch to the end, write a few transactions on the source, start fetch again with the failing PUTs.

        Failing PUTs of the binlog object: fetch exits with 1; the stored binlog.000002 is 308,063 bytes (source: 154,699), its metadata size 154,699. A clean fetch exits with 0 and leaves exact copies.

        Failing PUTs of the binlog metadata (binlog.000002.json): fetch exits with 1; the stored binlog.000002 is 308,063 bytes and its metadata size is also 308,063. Every later fetch exits with 1: cannot fetch binlog event: Client requested source to start replication from position > file size: CR_1236.

      Impact

        An S3 outage or throttling period that outlasts the SDK's retries corrupts the binlog being written. Readers of the storage (pull replicas, restores using the stored binlogs) get the duplicated events.

        When the metadata write was the one that failed, the corruption is permanent. In position mode streaming then stops for good (the resume position is past the end of the source's binlog) until the storage is repaired by hand. In GTID mode resuming does not use that position, so it is expected to continue silently with the duplicated events in the stored binlog (not verified).

        The filesystem backend is affected the same way, and there a single failure is enough because nothing retries: any failure while saving the binlog metadata (opening, writing, syncing or renaming binlog.NNNNNN.json.tmp, with ENOSPC or EIO) leaves the stored binlog.000002 at 308,063 bytes for the source's 154,699, as on S3. A full disk is enough to trigger it.

      Expected behaviour

      A failed write leaves the stored binlog and its metadata at the last complete state, and no data is ever written twice: either the retry continues from what is actually stored, or the storage stops accepting writes after a failure.

      Suggested fix

        Make write_event_block() all or nothing: on failure, restore the stream to the stored size (truncate the S3 temporary file, or the file on the filesystem backend) and leave the in-memory size unchanged; increase the size only after the metadata is saved.

        Do not flush again in the destructor after a write has failed, or flush only after re-reading the stored size.

        On start, check that each binlog's size in its metadata matches the end of its last complete event (the storage does not parse the stored data today; see the TODO in validate_binlog_index()).

      Tests

        extra/qa/s3_fault_sweep.py injects every fault of extra/qa/s3_fault_proxy.py into every kind of S3 request fetch makes, once and six times in a row. Single failures are all retried transparently; six failing PUTs of the binlog object or of its metadata produce this result.

        The randomized crash test extra/qa/fetch_crash_test.py with --storage s3 --s3-fault-control covers the same faults in generated sequences.

        extra/qa/disk_fault_sweep.py injects file system failures into the filesystem backend with the LD_PRELOAD library extra/qa/fsfault: every failure of the binlog metadata save (16 cases) produces this result; failures writing the binlog data itself are handled correctly.

      Verified on Linux (Ubuntu 24.04, GCC 14, debug build, AWS SDK C++ 1.11.774) against Versity S3 Gateway 1.8.0 behind s3_fault_proxy.py, MySQL 8.4.8, with the sweep and a targeted reproduction showing object and metadata sizes before and after a clean fetch; and on the filesystem backend with the disk fault sweep.         StatusOpen
PriorityHigh
Componentbinsrv (filesystem_storage_backend)

      Copy summaryCopy description

      Summary

      The filesystem backend writes binlog data through a std::ofstream: do_write_data_to_stream() calls write() and flush(), and do_close_stream() only closes the file (filesystem_storage_backend.cpp). flush() hands the data to the kernel's page cache; nothing ever calls fsync on a binlog data file. The binlog metadata, which records the binlog's size, is written with put_object(), which syncs the file and the directory (filesystem_storage_backend.cpp:144-159). After every checkpoint the metadata on disk is therefore durable, while the data it describes may not be.

      After a power loss or a kernel crash (a process crash keeps the page cache, so it is not affected), a binlog can be shorter on disk than its metadata says. The start-up recovery only handles the opposite case, a binlog longer than its metadata, which it truncates; this case it rejects.

      Reproduction

        Cause: the disk fault sweep (extra/qa/disk_fault_sweep.py), which intercepts every fsync in the storage directory, saw fsync calls for metadata and index files and none for any binlog data file during a complete fetch with two binlogs.

        Consequence: after a complete fetch, cutting the last 1,000 bytes off the last stored binlog (binlog.000002, 1,335 bytes, metadata size 1,335), as lost page-cache data would, makes every start fail: std::exception caught: cannot perform recovery - size from the binlog metadata is bigger than the actual binlog file size. For a binlog other than the last, the error is size from the binlog metadata does not match the actual binlog size.

      Impact

        After a power loss or kernel crash during normal operation, the Binlog Server cannot start in any mode until the storage is repaired by hand. A binlog server exists to keep binlogs safe through failures of the source, so it should survive failures of its own host.

        The data lost is what the metadata already recorded as stored: the GTID sets and positions in the metadata claim transactions that are not in the file.

        S3 storage is not affected: each upload is durable when it returns.

      Expected behaviour

      Binlog data is durable before the metadata that describes it, so after a crash of any kind the data on disk is at least as long as its metadata says, and the existing recovery (truncating extra data) applies.

      Suggested fix

        Sync the binlog data file (fdatasync on the stream's file descriptor, for example by writing through a POSIX file descriptor instead of std::ofstream) before save_binlog_metadata() in storage_core::write_event_block(), and when a binlog is closed.

        On start, treat a last binlog shorter than its metadata as the result of a crash: truncate the metadata (size, GTIDs and timestamps) back to the last complete transaction found in the file and stream the rest again from the source, instead of refusing to open the storage.

      Tests

        extra/qa/disk_fault_sweep.py with extra/qa/fsfault: the fsync rules targeting binlog data files are never hit.

        A power-loss test would need a VM or a file system that can drop unsynced data (for example dm-log-writes or a dm-flakey target); the reproduction above simulates the resulting state.

      Verified on Linux (Ubuntu 24.04, GCC 14, debug build) by reading the backend code, with the disk fault sweep (no fsync of binlog data files), and with the simulated state above against MySQL 8.4.8. A real power loss was not tested. Open on upstream main @ ee82afa.

That fixes the request at position 4 only. A request at any other position takes a different path: sender_context starts in the start_from_offset state, and handle_start_states() first calls fetch_fde_from_storage() to read the binlog's FORMAT_DESCRIPTION event. On an empty storage that fetch now succeeds with an empty buffer, which is shorter than a common header, so fetch_fde_from_storage() returns false, get_event() fails, and handle_binlog_dump_command() logs failed to fetch next event block and closes the connection: the failure PBS-91 describes, on the position-based path.

      This is not a regression: before PBS-91 the same request failed one step earlier, in the storage.

      Reproduction

        Create a sender_context on an empty storage for binlog.000001 at position 127 (the end of the FORMAT_DESCRIPTION event the binlog will start with), as handle_binlog_dump_command() does for a COM_BINLOG_DUMP with that name and position.

        Call get_event(): it returns false instead of EOF (true with an empty event).

        For comparison, the same request at position 4, with or without a binlog name, returns EOF until the binlog is written and then streams it from the beginning.

      Through pull this corresponds to, for example, mysqlbinlog --read-from-remote-server --stop-never --start-position=<N> binlog.000001 started right after binlog_server pull, before the collector receives the first ROTATE from the source.

      Impact

        A client that resumes from its last position (a replica repointed at a freshly started Binlog Server, or mysqlbinlog --stop-never restarted with --start-position) is disconnected during PBS startup, instead of waiting for the data. mysqlbinlog exits; a client that retries succeeds only once the storage holds the binlog.

        A non-blocking dump gets a closed connection instead of an EOF packet.

        The window is short (from PBS start until the first ROTATE from the source is stored), as in PBS-91, and grows when the collector is slow to connect to the source.

      Expected behaviour

      A request at any position behaves like one at position 4 while the storage is empty: EOF (and polling, for a blocking dump) until the binlog exists, then the artificial ROTATE and FORMAT_DESCRIPTION events and the events from the requested position. Once the storage holds binlogs, a request for a binlog that is not there still fails, as today.

      Suggested fix

      In fetch_fde_from_storage() (or handle_start_states()), treat an empty buffer returned for an empty storage as EOF: return true with an empty event and stay in the start_from_offset state, so the next call tries again. Keep returning false for a binlog that exists but is shorter than a FORMAT_DESCRIPTION event (truncated or corrupt).

      Tests

        tests/sender_context_property_test.cpp: EmptyStorageIsPolledUntilTheBinlogArrivesFromPosition polls a reader on an empty storage 1 to 5 times at a generated event boundary, then writes the binlog and requires the artificial ROTATE (with the requested position), an artificial FORMAT_DESCRIPTION and the remaining events byte for byte. It fails in every run today, shrinking to a binlog holding only its FORMAT_DESCRIPTION event and a request at position 127: poll 1 of an empty storage, resuming at position 127, failed instead of reporting EOF.

        The position-4 counterpart, EmptyStorageIsPolledUntilTheBinlogArrives, passes with PBS-91 and fails without it (checked by restoring the pre-PBS-91 rule).

        The MTR test added with PBS-91, rs_blocking_dump_empty_storage, dumps from position 4 only. A copy that passes --start-position would cover this end to end.

      Verified on Linux (Ubuntu 24.04, GCC 14, debug build) with the property test, on upstream main @ fd8a2d5. Not yet reproduced end to end with mysqlbinlog against pull.
