## Gaps

Each gap describes a failure class the catalog does not cover, written so it can serve as a targeted-discovery focus. The gap-fill properties are not written here; they are merged into the catalog afterwards, using the same deduplication process as discovery.

| ID | Gap | Raised by | Status |
|---|---|---|---|
| G1 | **Source restored from its own backup.** The source is rewound to an earlier physical backup and keeps its `server_uuid`. Its GNOs are then reused with different content. MySQL rejects a GTID dump only while the request holds more of the server's own UUID than it has executed (`rpl_binlog_sender.cc:918-921`), so PBS fails closed until the rewound source has committed enough new transactions, then silently continues. The storage ends up holding GTIDs whose content no server has. A ticket-25 fix based on `server_uuid` would not catch this. | WC W4 | Filled: `source-rewind-never-silently-continued` (P1, new; cross-referenced with `source-swap-never-silently-accepted`) |
| G2 | **Replay-restore oracle.** No oracle applies the backup. Replay the stored binlogs (decrypted offline) into a scratch `mysqld` from the generic tarball, starting from an empty initial state, and compare `CHECKSUM TABLE` of the workload schema with the source. Run it per mode (position, GTID, rewrite, encrypted). It checks semantics where the byte oracles are weak: rewrite, trailing events after a ROTATE, XA and compressed transactions. | WC W5 | Filled: `stored-binlogs-replay-to-source-state` (P1, new) |
| G3 | **Checkpoint bound on unpersisted data (SG8, RPO).** Split out of `collector-memory-bounded-by-checkpoint`. The size half is the SUT `ALWAYS(event_buffer_.size() ≤ checkpoint_size + open transaction + one event)`, which needs no memory limit. The interval half is a workload check: a transaction committed at t is stored by t + `checkpoint_interval` + `read_timeout` + δ while PBS is connected. The `read_timeout` term is there because the interval checkpoint fires only when an event arrives (LG3). Evaluated in quiet windows. | WC W6, CB F11 (LG3 freshness), AF F5 (collector-memory row) | Filled: `checkpoint-bounds-unpersisted-data` (P1, split out of `collector-memory-bounded-by-checkpoint`; R27 applied with the split) |
| G4 | **Fetch convergence liveness.** After faults stop, fetch reaches exit 0 within N attempts. Today the P0 exactly-once oracle is evaluated only after a final fetch exits 0, so a wedge, a crash loop or CR_1236 after ticket 18 shows up as silence rather than a failure. | CB F4 | Filled: `fetch-converges-after-faults-stop` (P1, new; cross-referenced with `pull-chain-converges-after-heal`) |
| G5 | **The source purges binlogs past PBS's resume point.** PBS must fail closed with a non-zero exit, store no new bytes, keep the storage openable, and never skip ahead to a later file in position mode. Under the supervisor the expected outcome is a crash loop, which the property should state explicitly. Run it as a flagged workload action so it does not swamp the exactly-once runs. | CB F5, WC W13 | Filled: `source-purge-past-resume-point-fails-closed` (P2, new) |
| G6 | **S3-specific recovery.** Two cases: (a) a kill or failed re-upload during `resize_object` in startup recovery (download, truncate, re-upload); (b) the `tmp_fstream_` failbit staying set after one failed PutObject, so every later write fails. Also record A10 (stale short-range read) as an explicit exclusion, since the harness uses Versity. | CB F7 | Filled: `s3-whole-object-put-publishes-intended-bytes` (P2, new; A10 recorded as an explicit exclusion) |
| G7 | **In-contract retention cycle.** Stop pull, run `purge_binlogs`, restart pull. The storage stays openable, survivors are intact, and clients that reconnect, including ones asking for just-purged files or for an empty name, get a correct stream or an ERR. `pull_fs` has no purge today, and purge beside pull exists only as misuse. | WC W7, AF F4 (purge anchors), CB F9 (purge × encryption, partly) | Filled: `pull-retention-cycle-keeps-serving-survivors` (P1, new) |

The gap-fill properties include a new kind of oracle (G2, apply-based restorability) and a new source-identity scenario (G1). They are now merged (2026-10-13), so a short second evaluation pass limited to `stored-binlogs-replay-to-source-state` and `source-rewind-never-silently-continued` is warranted. G3-G7 extend existing categories and do not need one on their own.
